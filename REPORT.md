# Звіт до лабораторної роботи №1

## 1. Тема, номер роботи та варіант

Лабораторна робота №1.

Тема: «Розгортання Java-проєкту та базова обробка даних».

Предметна область: метеостанція.

Варіант: 18.

Операційна система: Windows.

## 2. Мета роботи

Мета роботи — створити базову версію консольної Java-програми та підготувати структуру репозиторію для її подальшого розвитку.

На першому рівні реалізовано читання текстових даних, перевірку коректності записів, базові числові обчислення, форматований вивід результатів у консоль і текстовий файл.

Для варіанта 18 «Метеостанція» програма обробляє погодні спостереження та визначає кількість коректних записів, мінімальну температуру, середню вологість і найбільшу швидкість вітру.

## 3. Постановка задачі

Потрібно розробити консольну Java-програму для обробки даних метеостанції.

Один запис має формат:

`date;temperature;humidity;pressure;wind`

Поля запису:
- `date` — дата спостереження, `String`;
- `temperature` — температура, `double`;
- `humidity` — вологість, `double`;
- `pressure` — атмосферний тиск, `double`;
- `wind` — швидкість вітру, `double`.

Програма повинна:
1. прочитати записи з UTF-8 файла;
2. перевірити кожний рядок;
3. повідомити номер і причину пропуску некоректного рядка;
4. не враховувати хибні записи під час обчислень;
5. визначити кількість коректних записів;
6. знайти мінімальну температуру;
7. обчислити середню вологість;
8. знайти найбільшу швидкість вітру;
9. сформувати один звіт;
10. вивести звіт у консоль і записати його у файл.

## 4. Структура програми

Після виконання третього рівня проєкт має таку основну структуру:

```text
kzp-labs-popovych/
├── .github/
│   └── workflows/
│       └── ci.yml
├── .mvn/
│   └── wrapper/
│       └── maven-wrapper.properties
├── ai/
│   ├── manager.md
│   └── devops.md
├── data/
│   └── input.csv
├── src/
│   ├── main/
│   │   └── java/
│   │       └── ua/
│   │           └── lpnu/
│   │               └── kzp/
│   │                   └── Main.java
│   └── test/
│       └── java/
│           └── ua/
│               └── lpnu/
│                   └── kzp/
│                       └── MainTest.java
├── .editorconfig
├── .gitattributes
├── .gitignore
├── mvnw
├── mvnw.cmd
├── pom.xml
├── README.md
└── REPORT.md
```

Файл `Main.java` містить консольну програму для обробки записів метеостанції.

Файл `MainTest.java` містить JUnit 5 тести для перевірки коректних, помилкових і граничних сценаріїв.

Файл `pom.xml` описує Maven-проєкт, залежності, SpotBugs і створення виконуваного JAR.

Файли `mvnw`, `mvnw.cmd` та каталог `.mvn/wrapper/` утворюють Maven Wrapper.

Файл `.github/workflows/ci.yml` описує GitHub Actions workflow для автоматичної перевірки проєкту на Ubuntu, Windows і macOS.

Каталог `ai/` містить описи ролей Менеджера та DevOps, які використовувалися під час виконання роботи.

Каталоги `target/` та `out/` не додаються до Git, оскільки містять результати, які можна автоматично відтворити під час збірки або запуску програми.

## 11. Відповіді на контрольні питання

1. `pom.xml` описує Maven-проєкт, його координати, залежності, версію Java та плагіни.

2. Фаза `test` запускає тести, `verify` виконує перевірки до завершення життєвого циклу перевірки, а `package` створює пакет програми, у цьому проєкті — JAR.

3. Maven Wrapper дозволяє використовувати зафіксовану версію Maven без необхідності окремо встановлювати однаковий Maven на кожному комп'ютері.

4. Метод `main` є точкою входу консольної Java-програми.

5. Примітивні типи зберігають прості значення. `String` є посилальним типом і представляє об'єкт-рядок.

6. Середнє обчислюється як `double`, щоб не втратити дробову частину.

7. Якщо метод перетворення числа отримує текст, який не можна перетворити, виникає `NumberFormatException`.

8. Помилковий рядок не можна пропускати без повідомлення, оскільки користувач повинен знати, які дані не потрапили до обчислень.

9. `split(";", -1)` зберігає порожнє останнє поле.

10. `Path.of` дозволяє працювати зі шляхами незалежно від конкретної операційної системи.

11. Явне UTF-8 забезпечує однакове кодування текстових файлів на різних ОС.

12. `%n` створює системно коректний роздільник рядків.

13. Для варіанта 18 перевіряються кількість полів, дата, числові значення та недопустимі від'ємні значення. Від'ємна температура є допустимою.

14. Коректність середнього перевіряється тестом із кількома значеннями, для яких очікуваний результат відомий заздалегідь.

15. Статичний аналізатор перевіряє програму на потенційні дефекти без звичайного сценарію її виконання.

16. GitHub Actions автоматично запускає перевірки після `push` і `pull_request` та дозволяє виконати ті самі тести на різних операційних системах.

17. GitHub Issue для дефекту має містити опис проблеми, кроки відтворення, очікувану і фактичну поведінку.

18. У розділі академічної доброчесності потрібно зафіксувати інструменти ШІ, їхні ролі, запити, прийняті рекомендації, виправлені помилки та власний внесок.

19. DevOps відповідає за інфраструктуру збірки й CI, а Валідатор — за перевірку поведінки та крайових випадків.

### 4. Клас-сутність `WeatherReading`

1. **Навіщо потрібен клас-сутність?**

## Базовий тип WeatherReading

`WeatherReading` є абстрактним базовим класом.

У ньому зберігаються спільні поля:

- `date`;
- `temperature`;
- `humidity`;
- `pressure`;
- `wind`;
- `kind`.

Спільні правила валідації також знаходяться у базовому класі.

Для `WeatherReading` обрано абстрактний клас, а не інтерфейс,
оскільки `DailyReading` і `StormReading` мають спільний стан
і спільну реалізацію перевірок.

Поліморфна операція оголошена як:

`dangerIndex()`

Її реалізація визначається конкретним підтипом.

## Підтипи

### DailyReading

`DailyReading` представляє звичайне погодне спостереження.

Запис належить до цього типу, якщо швидкість вітру
менша за `15.0`.

Індекс небезпеки:

`wind + humidity / 20.0`

### StormReading

`StormReading` представляє штормове погодне спостереження.

Запис належить до цього типу, якщо швидкість вітру
становить не менше `15.0`.

Індекс небезпеки:

`wind * 2.0 + humidity / 10.0`

Обидва підтипи перевизначають `dangerIndex()` через `@Override`.

Межу `15.0` та формули індексу небезпеки обрано
як проєктне рішення для реалізації різної поведінки підтипів.

## Enum WeatherKind

Для категорії погодного спостереження створено enum `WeatherKind`.

Використовуються два значення:

- `DAILY`;
- `STORM`.

Enum використовується безпосередньо в моделі
та дозволяє уникнути використання довільних текстових значень
для позначення типу погодного запису.

## Equals і hashCode

Для `WeatherReading` реалізовано узгоджені методи
`equals()` і `hashCode()`.

Два погодні записи вважаються логічно рівними,
якщо вони належать до одного конкретного підтипу
та мають однакові:

- дату;
- температуру;
- вологість;
- атмосферний тиск;
- швидкість вітру;
- `WeatherKind`.

Коректність рівності перевірено через `HashSet`.

Два однакові `DailyReading` не створюють дублікати
в множині, а рівні об'єкти мають однаковий `hashCode`.

Об'єкти різних підтипів не вважаються рівними.

## Поліморфізм

Об'єкти `DailyReading` і `StormReading`
зберігаються у колекції типу `List<WeatherReading>`.

Обчислення індексу небезпеки виконується через:

`reading.dangerIndex()`

Змінна `reading` має тип `WeatherReading`,
але під час виконання Java викликає реалізацію
фактичного підтипу.

У коді звітності не використовується центральний
`if` або `switch` для вибору реалізації `dangerIndex()`.

Таким чином додавання нового підтипу не потребує
переписування коду обчислення показників у `Main`.

## Завдання із зірочкою

Ієрархію `WeatherReading` реалізовано як `sealed`.

Базовий клас явно дозволяє лише:

- `DailyReading`;
- `StormReading`.

Обидва підтипи є `final`, тому перелік безпосередніх підтипів
ієрархії повністю відомий компілятору.

Для обробки sealed-ієрархії використано pattern matching `switch`.

У `switch` окремо обробляються `DailyReading` і `StormReading`.
Оскільки `WeatherReading` є sealed і всі дозволені підтипи відомі,
компілятор може перевірити вичерпність `switch`.

Якщо додати новий дозволений підтип і не додати відповідний `case`,
компілятор вимагатиме доповнити `switch`.

При цьому `switch` не використовується для обчислення
`dangerIndex()`, оскільки ця логіка вже реалізована
поліморфно в підтипах і не повинна дублюватися.

## Відповіді на контрольні питання

1. **Яку спільну проблему розв'язує базовий тип у предметній області?**  
Базовий тип зберігає спільні поля й правила для всіх підтипів. У нашій моделі `WeatherReading` містить загальні погодні дані та валідацію для `DailyReading` і `StormReading`.

2. **Чим відрізняються extends і implements?**  
`extends` використовується для успадкування класу, а `implements` — для реалізації контракту інтерфейсу.

3. **Навіщо базовий клас може бути abstract?**  
Щоб заборонити створення загального об'єкта, для якого немає конкретної поведінки, і змусити підтипи реалізувати абстрактні методи.

4. **Яку роль виконує super(...) у конструкторі підтипу?**  
`super(...)` викликає конструктор базового класу і передає йому спільний стан об'єкта.

5. **Що перевіряє анотація @Override?**  
Вона дозволяє компілятору перевірити, що метод справді перевизначає метод базового типу.

6. **Що таке поліморфізм і як він усуває розгалуження за типом?**  
Поліморфізм дозволяє працювати з різними підтипами через один базовий тип. Виклик `reading.dangerIndex()` автоматично використовує реалізацію фактичного підтипу без `if` за типом.

7. **Коли краще використати інтерфейс, а коли абстрактний клас?**  
Інтерфейс зручний для опису спільної можливості, а абстрактний клас — коли об'єкти мають спільні поля та частину реалізації. Для `WeatherReading` обрано абстрактний клас через спільний стан і валідацію.

8. **Що означає відношення «є різновидом» і чим воно відрізняється від композиції?**  
«Є різновидом» означає успадкування: `StormReading` є різновидом `WeatherReading`. Композиція означає, що один об'єкт містить інший як свою частину.

9. **Для чого використовують enum із полями та методами?**  
Enum задає фіксований набір допустимих значень і може містити додаткові дані, наприклад текстовий підпис.

10. **Чому значення enum можна порівнювати через ==?**  
Кожна enum-константа існує в одному екземплярі, тому `==` коректно порівнює її ідентичність.

11. **Які правила має виконувати пара equals/hashCode?**  
Якщо два об'єкти рівні через `equals()`, вони повинні мати однаковий `hashCode()`. Рівність також повинна бути рефлексивною, симетричною, транзитивною та стабільною.

12. **Чому змінне поле небезпечне для об'єкта, який є ключем HashMap?**  
Якщо поле, що бере участь у `hashCode()`, зміниться після додавання об'єкта, колекція може більше не знайти цей ключ у правильному bucket.

13. **Чому два об'єкти різних підтипів можуть бути нерівними за однакових даних?**  
Тому що підтип є частиною логічної сутності. У нашій реалізації `equals()` додатково перевіряє конкретний клас через `getClass()`.

14. **Як поліморфна колекція обробляє об'єкти різних підтипів?**  
`List<WeatherReading>` може містити `DailyReading` і `StormReading`, а виклик спільного методу автоматично переходить до реалізації відповідного підтипу.

15. **Які тести доводять, що підтипи мають різну поведінку?**  
Тести, де через змінні типу `WeatherReading` викликається `dangerIndex()` для `DailyReading` і `StormReading` та отримуються різні результати.

16. **Які тести доводять коректність рівності в HashSet?**  
Перевірка, що два рівні об'єкти мають однаковий `hashCode()` і після додавання обох у `HashSet` розмір множини залишається 1.

17. **Що контролює sealed і навіщо потрібен permits?**  
`sealed` обмежує перелік класів, які можуть успадковувати базовий тип, а `permits` явно перелічує дозволені підтипи.

18. **Чому switch за підтипами не повинен дублювати поліморфні методи?**  
Інакше логіка поведінки розміщується у двох місцях. Поліморфну поведінку краще залишати всередині конкретних підтипів.

19. **Які попередні тести та результати потрібно зберегти після перебудови?**  
Потрібно зберегти всі тести Lab 1 і Lab 2, формат CSV та попередні показники: кількість коректних записів, мінімальну температуру, середню вологість і найбільшу швидкість вітру.

20. **Яке рішення у Вашій ієрархії найкраще демонструє перевагу поліморфізму?**  
Виклик `reading.dangerIndex()` у циклі по `List<WeatherReading>`. Код не перевіряє, чи це `DailyReading`, чи `StormReading`, але отримує правильну реалізацію автоматично.

## П'ять Stream API запитів

### 1. Фільтрація за швидкістю вітру

Метод:

`filterByWind()`

Джерело:

`List<WeatherReading>`

Умова:

`wind > threshold`

Використовується:

`filter`

Результат:

`List<WeatherReading>`

Запис із швидкістю вітру, яка точно дорівнює порогу, до результату не входить.

### 2. Отримання дат

Метод:

`dates()`

Використовується:

`map(WeatherReading::getDate)`

Результат:

`List<String>`

### 3. Середня температура за місяцем

Метод:

`averageTemperatureByMonth()`

Зовнішнім ключем є місяць у форматі:

`YYYY-MM`

Використовуються:

- `groupingBy`;
- `averagingDouble`.

Результат:

`Map<String, Double>`

### 4. Статистика температури

Метод:

`temperatureStatistics()`

Використовується:

`summarizingDouble`

Результат:

`DoubleSummaryStatistics`

Статистика містить:

- `count`;
- `sum`;
- `min`;
- `max`;
- `average`.

### 5. Top-N за температурою

Метод:

`topByTemperature()`

Основний критерій:

температура за спаданням.

Другий критерій:

дата за зростанням.

Після сортування використовується `limit(N)`.

Результат:

`List<WeatherReading>`

## Групування і статистика

Для групування за місяцем використовується:

`Collectors.groupingBy(...)`

Середня температура в кожній групі обчислюється через:

`Collectors.averagingDouble(...)`

Для статистики температури використовується:

`Collectors.summarizingDouble(...)`

Для порожньої колекції `DoubleSummaryStatistics` має:

- `count = 0`;
- `sum = 0.0`;
- `average = 0.0`;
- `min = Double.POSITIVE_INFINITY`;
- `max = Double.NEGATIVE_INFINITY`.

Порожня колекція не спричиняє помилки.

## Складений компаратор

Для top-N використовується складений компаратор:

`Comparator.comparingDouble(WeatherReading::getTemperature)
        .reversed()
        .thenComparing(WeatherReading::getDate)`

Спочатку записи сортуються за температурою за спаданням.

Якщо температура однакова, використовується дата за зростанням.

Після формування повного порядку застосовується:

`limit(N)`

Перевірено:

- `N = 0`;
- `N`, більше за розмір колекції;
- набір із шести записів для top-5;
- однакову температуру і другий критерій сортування.

## Optional-пошук

Метод:

`findByDate()`

виконує пошук погодного спостереження за датою.

Використовуються:

`filter(...).findFirst()`

Результат:

`Optional<WeatherReading>`

Якщо запис знайдено, `Optional` містить відповідний `WeatherReading`.

Якщо дата відсутня:

`Optional.empty()`

Якщо декілька записів мають однакову дату, `findFirst()` повертає перший запис у початковому порядку.

## Порівняння реалізацій

Stream API дозволив винести запити до колекції в окремий клас і описати їх декларативно.

`filter` безпосередньо показує умову відбору.

`map` показує перетворення одного представлення даних на інше.

`groupingBy` описує побудову груп без ручного керування картою.

`summarizingDouble` формує основну статистику одним collector.

Складений `Comparator` задає повний порядок top-N.

`Optional` явно показує, що результат пошуку може бути відсутнім.

Перевагу Stream API не варто оцінювати лише за кількістю рядків. Основна перевага полягає у виразному поділі джерела, проміжних операцій і кінцевого результату.

Вхідна колекція під час запитів не змінюється, що підтверджено окремим тестом.

## Відповіді на контрольні питання

1. **Чим потік відрізняється від колекції?**  
Колекція зберігає дані, а Stream використовується для виконання послідовності операцій над цими даними. Потік не є сховищем і після кінцевої операції повторно не використовується.

2. **Які частини має типовий конвеєр Stream API?**  
Джерело даних, проміжні операції та кінцева операція. Наприклад: `stream() → filter() → map() → toList()`.

3. **Чому проміжні операції називають лінивими?**  
Вони не обробляють дані одразу. Виконання починається після виклику кінцевої операції.

4. **Що робить filter і який тип має його предикат?**  
`filter` залишає елементи, для яких умова повертає `true`. Умова має тип `Predicate<T>`.

5. **Чим map відрізняється від mapToDouble?**  
`map` створює звичайний потік об'єктів, а `mapToDouble` — спеціалізований `DoubleStream`.

6. **Для чого застосовується distinct і від чого залежить його результат?**  
`distinct` прибирає дублікати. Для об'єктів результат залежить від реалізації `equals()` і `hashCode()`.

7. **Чому sorted().limit(N) відрізняється від limit(N).sorted()?**  
`sorted().limit(N)` спочатку впорядковує весь набір і після цього вибирає N найкращих елементів. `limit(N).sorted()` сортує лише перші N елементів початкового потоку.

8. **Яку роль виконує кінцева операція?**  
Кінцева операція запускає виконання конвеєра та формує його результат.

9. **Коли застосовується Collectors.joining?**  
Коли декілька текстових елементів потрібно об'єднати в один рядок.

10. **Як groupingBy будує карту груп?**  
Для кожного елемента обчислюється ключ, після чого елементи з однаковими ключами накопичуються в одній групі.

11. **Як отримати суму в кожній групі через downstream collector?**  
До `groupingBy` можна передати downstream collector, наприклад `summingDouble`.

12. **Які показники містить DoubleSummaryStatistics?**  
Кількість, суму, мінімум, максимум і середнє значення.

13. **Які значення має статистика для порожнього потоку?**  
`count`, `sum` і `average` дорівнюють нулю, `min` має значення `POSITIVE_INFINITY`, а `max` — `NEGATIVE_INFINITY`.

14. **Як утворюється складений компаратор?**  
Спочатку задається основний критерій через `comparing` або `comparingDouble`, після чого додається другий критерій через `thenComparing`.

15. **Чому reversed() потрібно застосовувати до окремого ключа до thenComparing?**  
Щоб змінити напрямок основного критерію, але залишити другий критерій у потрібному напрямку.

16. **Яку проблему розв'язує Optional у методі пошуку?**  
`Optional` явно показує, що результат може бути відсутнім, без використання `null`.

17. **Чим відрізняються orElse, orElseThrow і ifPresent?**  
`orElse` повертає запасне значення, `orElseThrow` генерує виняток, якщо значення немає, а `ifPresent` виконує дію лише тоді, коли значення існує.

18. **Чому накопичення результату через зовнішній змінний список у forEach небажане?**  
Це створює побічний ефект. Для формування результатів краще використовувати `toList()` або `collect()`.

19. **Які властивості мають бути перевірені під час рефакторингу циклу на потік?**  
Потрібно перевірити результати, порядок, дублікати, порожній вхід, крайові значення, відсутній пошук, поведінку limit, відсутність мутації колекції та проходження попередніх тестів.

20. **За яких умов паралельний потік може бути виправданим?**  
Коли набір даних достатньо великий, операції незалежні та достатньо складні, а виграш від паралельного виконання перевищує додаткові витрати на розподіл роботи.

`add(T)`

## Анотація @CsvColumn

Створено власну анотацію:

`@CsvColumn`

Використано:

`@Retention(RetentionPolicy.RUNTIME)`

та:

`@Target(ElementType.FIELD)`

Анотація має один елемент:

`String value()`

`RUNTIME` потрібен тому, що exporter читає анотацію під час виконання програми через reflection.

`FIELD` обмежує застосування анотації полями класу.

Поля `WeatherReadingRecord`, які експортуються, позначені `@CsvColumn`.

Назви CSV-стовпців беруться тільки зі значень анотації.

Порядок стовпців не залежить від порядку, у якому JVM повернула поля.

Поля сортуються за Java-іменами.

Для `WeatherReadingRecord` порядок Java-полів після сортування:

`date → humidity → pressure → temperature → wind`

Тому фактичний CSV-заголовок має вигляд:


## Рефлексивний експортер

Створено універсальний:

`CsvExporter<T>`

Експортер не містить перевірок на:

`WeatherReadingRecord`

або інші конкретні предметні типи.

Він може працювати з будь-яким класом, поля якого позначені `@CsvColumn`.

Алгоритм роботи exporter-а:

1. отримати поля класу через `getDeclaredFields()`;
2. залишити поля з `@CsvColumn`;
3. детерміновано відсортувати їх;
4. перевірити можливість доступу через `trySetAccessible()`;
5. отримати назви CSV-стовпців з анотацій;
6. отримати значення полів через reflection;
7. виконати CSV-екранування;
8. сформувати заголовок і рядки;
9. записати результат у UTF-8 файл.

CSV записується через:

`Path`

і:

`Files.writeString(...)`

з явним:

`StandardCharsets.UTF_8`

Для повторного запису використовується:

`StandardOpenOption.TRUNCATE_EXISTING`

тому після коротшого нового експорту у файлі не залишаються рядки попереднього експорту.

Експортер не змінює предметні об'єкти та вхідну колекцію.

## Імпорт і round-trip

Для читання CSV створено окремий:

`CsvParser`

Реалізовано:

- розбір одного CSV-запису;
- розбір повного CSV-документа;
- quoted-поля;
- кому всередині quoted-поля;
- подвоєні лапки `""`;
- multiline-поля;
- `LF`;
- `CRLF`.

Простий:

`split(",")`

не використовується, оскільки він не може відрізнити кому-роздільник від коми всередині quoted-поля та не підтримує multiline-CSV.

У `WeatherReadingRecord` реалізовано:

`fromCsv(...)`

та:

`fromFields(...)`

Під час імпорту:

- кількість полів перевіряється;
- `date` перетворюється на `LocalDate`;
- числові значення перетворюються на `double`;
- створюється новий `WeatherReadingRecord`;
- повторно виконується предметна валідація.

Повний файл читається через:

`Files.readString(path, StandardCharsets.UTF_8)`

Перший рядок CSV є заголовком і не перетворюється на предметний об'єкт.

Порожній CSV повертає порожній список.

Файл, який містить лише заголовок, також повертає порожній список предметних записів.

Round-trip має вигляд:

`об'єкти → CSV → об'єкти`

Тест створює початковий список, експортує його в CSV, читає файл назад та відновлює об'єкти.

Після цього виконується:

`assertEquals(original, restored)`

Тест підтверджує:

## Відповіді на контрольні питання

1. **Яку проблему розв'язує параметр типу в `Repository<T>`?**

Параметр `T` дозволяє одному класу repository працювати з різними типами об'єктів і при цьому зберігати перевірку типів під час компіляції.

2. **Чим параметризований клас відрізняється від raw type?**

У параметризованому класі тип елементів відомий компілятору. Raw type втрачає цю інформацію та може призвести до небезпечних приведень типів і помилок під час виконання.

3. **Навіщо `Predicate<? super T>` у методі пошуку?**

Такий параметр дозволяє передавати предикат для `T` або для його базового типу. Це робить API гнучкішим без втрати типобезпеки.

4. **Чому `all()` має повертати незмінний знімок?**

Щоб зовнішній код не міг випадково змінити внутрішню колекцію repository. `List.copyOf` створює безпечне представлення поточного стану.

5. **Що таке checked exception і коли він доречний у цій роботі?**

Checked exception — це виняток, який потрібно обробити або оголосити через `throws`. Він доречний для файлових і storage-операцій, де помилка є очікуваною ситуацією, яку викликаючий код повинен усвідомлено обробити.

6. **Для чого зберігати `cause` власного винятку?**

`cause` зберігає початкову технічну причину проблеми. Наприклад, `DataStorageException` описує помилку на рівні storage, а всередині можна зберегти `IOException`, `NumberFormatException` або `DateTimeParseException`.

7. **Чим `Path` і `Files` кращі за складання шляху рядком?**

`Path` представляє шлях структуровано та коректно працює з особливостями різних операційних систем. `Files` надає стандартні методи читання та запису без ручного складання шляхів.

8. **Чому кодування потрібно задавати і під час запису, і під час читання?**

Якщо записати файл в одному кодуванні, а прочитати в іншому, текст може пошкодитися. Явний UTF-8 гарантує однакову інтерпретацію даних.

9. **Що роблять `@Retention(RUNTIME)` і `@Target(FIELD)`?**

`RUNTIME` зберігає анотацію доступною під час роботи програми. `FIELD` дозволяє застосовувати її саме до полів.

10. **Чому анотація не виконує експорт сама?**

Анотація є лише метаданими. Вона описує поле, а поведінку реалізує exporter, який читає цю інформацію через reflection.

11. **Чим `getDeclaredFields()` відрізняється від отримання публічних полів?**

`getDeclaredFields()` повертає поля, оголошені безпосередньо в класі, незалежно від модифікатора доступу. Отримання публічних полів бачить тільки `public` поля з урахуванням успадкування.

12. **Навіщо перевіряти `trySetAccessible()`?**

Тому що CSV-exporter повинен читати приватні поля. `trySetAccessible()` дозволяє перевірити, чи JVM реально дозволила такий доступ, а не припускати це.

13. **Чому порядок полів для CSV потрібно зробити детермінованим?**

Щоб однаковий клас завжди формував однаковий заголовок і порядок значень незалежно від JVM або ОС. Це також робить round-trip передбачуваним.

14. **Чому `split(",")` не підходить для загального CSV?**

Тому що кома може бути частиною quoted-поля. Також CSV може містити екрановані лапки та перенесення рядка всередині одного логічного запису.

15. **Як екрануються кома, лапка й перенесення рядка в CSV?**

Поле, що містить кому, лапку або перенесення рядка, береться у подвійні лапки. Подвійна лапка всередині такого поля записується двічі.

16. **Чому порожній список потребує окремого параметра `Class<T>`?**

Якщо список порожній, exporter не може визначити клас за першим об'єктом. `Class<T>` дає йому інформацію про поля та анотації навіть без жодного елемента.

17. **Чим універсальний exporter відрізняється від предметного `fromCsv`?**

Exporter не знає правил конкретної предметної області й працює через метадані. `fromCsv` належить предметному класу та знає конкретні типи, кількість полів і правила валідації.

18. **Які рівні помилок розрізняє програма?**

Програма розрізняє помилки валідації предметної моделі, формату CSV, перетворення значень, файлової системи та reflection.

19. **Що доводить тест round-trip?**

Він доводить, що після послідовності `об'єкти → CSV → об'єкти` відновлений список дорівнює початковому, тобто збереження не втратило значення, порядок або ключі.

20. **Чому виняток не можна поглинати порожнім `catch`?**

Тому що тоді програма приховує реальну причину помилки й може продовжити роботу з некоректним станом. Помилку потрібно або обробити, або передати вище зі зрозумілим повідомленням і `cause`.
