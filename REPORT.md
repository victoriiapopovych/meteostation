# Звіт до лабораторної роботи №1

## 1. Тема, номер роботи та варіант

Лабораторна робота №1.

Тема: «Розгортання Java-проєкту та базова обробка даних».

Предметна область: метеостанція.

Варіант: 18.

Операційна система: Windows.

## 2. Мета роботи

Мета роботи — створити базову версію консольної Java-програми та підготувати структуру репозиторію для її подальшого розвитку.

На першому рівні реалізовано читання текстових даних, перевірку коректності записів, базові числові обчислення, форматований вивід результатів у консоль і текстовий файл.

Для варіанта 18 «Метеостанція» програма обробляє погодні спостереження та визначає кількість коректних записів, мінімальну температуру, середню вологість і найбільшу швидкість вітру.

## 3. Постановка задачі

Потрібно розробити консольну Java-програму для обробки даних метеостанції.

Один запис має формат:

`date;temperature;humidity;pressure;wind`

Поля запису:
- `date` — дата спостереження, `String`;
- `temperature` — температура, `double`;
- `humidity` — вологість, `double`;
- `pressure` — атмосферний тиск, `double`;
- `wind` — швидкість вітру, `double`.

Програма повинна:
1. прочитати записи з UTF-8 файла;
2. перевірити кожний рядок;
3. повідомити номер і причину пропуску некоректного рядка;
4. не враховувати хибні записи під час обчислень;
5. визначити кількість коректних записів;
6. знайти мінімальну температуру;
7. обчислити середню вологість;
8. знайти найбільшу швидкість вітру;
9. сформувати один звіт;
10. вивести звіт у консоль і записати його у файл.

## 4. Структура програми

Після виконання третього рівня проєкт має таку основну структуру:

```text
kzp-labs-popovych/
├── .github/
│   └── workflows/
│       └── ci.yml
├── .mvn/
│   └── wrapper/
│       └── maven-wrapper.properties
├── ai/
│   ├── manager.md
│   └── devops.md
├── data/
│   └── input.csv
├── src/
│   ├── main/
│   │   └── java/
│   │       └── ua/
│   │           └── lpnu/
│   │               └── kzp/
│   │                   └── Main.java
│   └── test/
│       └── java/
│           └── ua/
│               └── lpnu/
│                   └── kzp/
│                       └── MainTest.java
├── .editorconfig
├── .gitattributes
├── .gitignore
├── mvnw
├── mvnw.cmd
├── pom.xml
├── README.md
└── REPORT.md
```

Файл `Main.java` містить консольну програму для обробки записів метеостанції.

Файл `MainTest.java` містить JUnit 5 тести для перевірки коректних, помилкових і граничних сценаріїв.

Файл `pom.xml` описує Maven-проєкт, залежності, SpotBugs і створення виконуваного JAR.

Файли `mvnw`, `mvnw.cmd` та каталог `.mvn/wrapper/` утворюють Maven Wrapper.

Файл `.github/workflows/ci.yml` описує GitHub Actions workflow для автоматичної перевірки проєкту на Ubuntu, Windows і macOS.

Каталог `ai/` містить описи ролей Менеджера та DevOps, які використовувалися під час виконання роботи.

Каталоги `target/` та `out/` не додаються до Git, оскільки містять результати, які можна автоматично відтворити під час збірки або запуску програми.

## 11. Відповіді на контрольні питання

1. `pom.xml` описує Maven-проєкт, його координати, залежності, версію Java та плагіни.

2. Фаза `test` запускає тести, `verify` виконує перевірки до завершення життєвого циклу перевірки, а `package` створює пакет програми, у цьому проєкті — JAR.

3. Maven Wrapper дозволяє використовувати зафіксовану версію Maven без необхідності окремо встановлювати однаковий Maven на кожному комп'ютері.

4. Метод `main` є точкою входу консольної Java-програми.

5. Примітивні типи зберігають прості значення. `String` є посилальним типом і представляє об'єкт-рядок.

6. Середнє обчислюється як `double`, щоб не втратити дробову частину.

7. Якщо метод перетворення числа отримує текст, який не можна перетворити, виникає `NumberFormatException`.

8. Помилковий рядок не можна пропускати без повідомлення, оскільки користувач повинен знати, які дані не потрапили до обчислень.

9. `split(";", -1)` зберігає порожнє останнє поле.

10. `Path.of` дозволяє працювати зі шляхами незалежно від конкретної операційної системи.

11. Явне UTF-8 забезпечує однакове кодування текстових файлів на різних ОС.

12. `%n` створює системно коректний роздільник рядків.

13. Для варіанта 18 перевіряються кількість полів, дата, числові значення та недопустимі від'ємні значення. Від'ємна температура є допустимою.

14. Коректність середнього перевіряється тестом із кількома значеннями, для яких очікуваний результат відомий заздалегідь.

15. Статичний аналізатор перевіряє програму на потенційні дефекти без звичайного сценарію її виконання.

16. GitHub Actions автоматично запускає перевірки після `push` і `pull_request` та дозволяє виконати ті самі тести на різних операційних системах.

17. GitHub Issue для дефекту має містити опис проблеми, кроки відтворення, очікувану і фактичну поведінку.

18. У розділі академічної доброчесності потрібно зафіксувати інструменти ШІ, їхні ролі, запити, прийняті рекомендації, виправлені помилки та власний внесок.

19. DevOps відповідає за інфраструктуру збірки й CI, а Валідатор — за перевірку поведінки та крайових випадків.

### Стан до і після рефакторингу

У лабораторній роботі №1 один погодний запис оброблявся як текстовий рядок.
Розбиття рядка на поля, перетворення чисел і перевірка значень виконувалися

Він зберігає дані одного погодного спостереження у `private final` полях
та перевіряє допустимість значень у конструкторі.

Для перетворення CSV-рядка використовується фабричний метод
`WeatherReading.fromCsv(String line)`.

Клас `Main` тепер відповідає за читання файла, формування списку
`WeatherReading`, обчислення статистики та формування звіту.

Зовнішня поведінка програми не змінилася:
формат CSV та показники звіту залишилися такими самими, як у лабораторній роботі №1.
