# Лабораторна робота №1

## Варіант
18 — Метеостанція

## Призначення програми
Консольна Java-програма читає погодні спостереження з текстового файла, перевіряє коректність записів, пропускає помилкові рядки та формує підсумковий звіт.

## Формат вхідних даних
Кожний рядок має формат:

date;temperature;humidity;pressure;wind

Приклад:

2026-09-01;18.5;62.0;1013.2;3.4

## Результати
Програма обчислює:
- кількість коректних записів;
- мінімальну температуру;
- середню вологість;
- найбільшу швидкість вітру.

## Файл за замовчуванням
Вхід:
data/input.csv

Вихід:
out/report.txt

## Запуск

Компіляція:

javac -encoding UTF-8 -d target/classes src/main/java/ua/lpnu/kzp/Main.java

Звичайний запуск:

java -cp target/classes ua.lpnu.kzp.Main

Довідка:

java -cp target/classes ua.lpnu.kzp.Main --help

Явне задання вхідного і вихідного файла:

java -cp target/classes ua.lpnu.kzp.Main --input data/input.csv --output out/custom-report.txt

## Лабораторна робота №2

Поточна версія для Lab 2: `2.0.0`.

У лабораторній роботі №2 виконано перехід від рядкового
представлення погодного запису до об'єктної моделі.

Основною сутністю є клас `WeatherReading` з полями:

- `date`;
- `temperature`;
- `humidity`;
- `pressure`;
- `wind`.

Поля зберігаються як `private final`.
Перевірка коректності значень виконується в конструкторі.

Для створення об'єкта з CSV-рядка використовується
статичний фабричний метод `WeatherReading.fromCsv(String line)`.

Для допоміжного незмінного значення використовується record
`TemperatureHumidity`.

### Порівняння Lab 1 і Lab 2

| Представлення запису | `String` і поля масиву | `WeatherReading` |

### Незмінність і Builder

Клас `WeatherReading` є незмінним:
він оголошений як `final`, усі поля мають модифікатор `private final`,
а setter-и відсутні.

Для зручного створення об'єктів реалізовано `WeatherReading.Builder`.
Метод `build()` викликає основний конструктор `WeatherReading`,
тому Builder не обходить правила валідації.

## Лабораторна робота №3

Поточна версія для Lab 3: `3.0.0`.

У лабораторній роботі №3 модель метеостанції розширено
за допомогою спадкування та поліморфізму.

`WeatherReading` використовується як абстрактний базовий клас.
Він містить спільні поля та правила валідації погодного спостереження.

Створено два конкретні підтипи:

- `DailyReading` — звичайне погодне спостереження;
- `StormReading` — штормове погодне спостереження.

Для категорії спостереження використовується enum `WeatherKind`
зі значеннями `DAILY` і `STORM`.

Поліморфною операцією є метод `dangerIndex()`.
Він оголошений у `WeatherReading` і має різну реалізацію
в `DailyReading` та `StormReading`.

Запис вважається штормовим, якщо швидкість вітру
становить не менше `15.0`.

Для `DailyReading` індекс небезпеки обчислюється як:

`wind + humidity / 20.0`

Для `StormReading`:

`wind * 2.0 + humidity / 10.0`

Об'єкти різних підтипів зберігаються у `List<WeatherReading>`,
а виклик `dangerIndex()` виконується через базовий тип
без центрального `if` або `switch` за конкретним підтипом.

Для `WeatherReading` реалізовано узгоджені `equals()` і `hashCode()`.
Рівність перевіряється також за допомогою `HashSet`.

Після розширення моделі всі попередні тести залишилися працездатними.
Загалом виконується 38 JUnit 5 тестів.

GitHub Actions перевіряє проєкт на Ubuntu, Windows і macOS
та публікує виконуваний JAR як artifact.

Формат CSV залишився сумісним із попередніми лабораторними роботами:

`date;temperature;humidity;pressure;wind`

Публічні класи, конструктори, enum і нетривіальні методи
Lab 3 задокументовані за допомогою Javadoc.

### Sealed-ієрархія

Базовий клас `WeatherReading` оголошено як `sealed`.

Через `permits` явно дозволено два підтипи:

- `DailyReading`;
- `StormReading`.

Обидва підтипи оголошені `final`.

Для демонстрації pattern matching реалізовано `switch`,
який формує текстовий опис підтипу.

`switch` не дублює логіку `dangerIndex()`,
оскільки індекс небезпеки й надалі обчислюється
поліморфно всередині конкретних підтипів.



## Лабораторна робота №4

Поточна версія для Lab 4: `4.0.0`.

У лабораторній роботі №4 обробку колекції погодних
спостережень перенесено на Java Stream API.

Для потокових запитів створено окремий клас
`WeatherReadingQueries`.

### Реалізовані Stream API запити

Для варіанта 18 «Метеостанція» реалізовано:

- `filterByWind()` — відбір записів, у яких швидкість
  вітру перевищує заданий поріг, через `filter`;

- `dates()` — отримання дат погодних спостережень
  через `map`;

- `averageTemperatureByMonth()` — групування записів
  за місяцем та обчислення середньої температури
  через `groupingBy` і `averagingDouble`;

- `temperatureStatistics()` — зведена статистика
  температури через `summarizingDouble`;

- `topByTemperature()` — вибір перших N записів
  за температурою за спаданням, а при однаковій
  температурі — за датою за зростанням;

- `findByDate()` — пошук першого запису за датою
  з результатом `Optional<WeatherReading>`.

Для top-N використовується складений компаратор:

`comparingDouble(...).reversed().thenComparing(...)`

Після сортування застосовується `limit(N)`.

### Зміни порівняно з Lab 3

У Lab 3 основні обчислення колекції виконувалися імперативно
за допомогою циклів.

У Lab 4 обробку винесено в окремі Stream API запити:

- відбір через `filter`;
- перетворення через `map`;
- групування через `groupingBy`;
- статистику через `summarizingDouble`;
- сортування через `sorted`, `thenComparing` і `limit`;
- пошук через `Optional`.

Зовнішній формат CSV та попередні показники звіту не змінено.

### Завдання із зірочкою

Реалізовано дворівневе групування:

`місяць → WeatherKind → середня температура`

Результат має тип:

`Map<String, Map<WeatherKind, Double>>`

Для цього використано `groupingBy` усередині `groupingBy`
та `averagingDouble`.

### Тестування

Усі запити перевірено JUnit 5 тестами.

Перевіряються:

- коректні дані;
- порожня колекція;
- межа умови `filter`;
- дубльована дата;
- `Optional.empty()` для відсутнього запису;
- однакова температура у top-N;
- другий критерій складеного компаратора;
- `limit(0)`;
- N, більший за розмір колекції;
- відсутність мутації вхідної колекції;
- дворівневе групування.

Загалом виконується 55 JUnit 5 тестів.

Усі попередні тести Lab 1–3 залишилися працездатними.

## Лабораторна робота №5

Поточна версія для Lab 5: `5.0.0`.

У лабораторній роботі №5 до проєкту додано
параметризоване сховище даних, універсальний
рефлексивний CSV-експорт та зворотне відновлення
об'єктів із CSV.

Для варіанта 18 «Метеостанція» використовується
клас `WeatherReadingRecord`.

### Repository<T>

Для зберігання об'єктів створено generic-клас:

`Repository<T>`

Реалізовано:

- `add(T)` — додавання об'єкта до сховища;
- `all()` — отримання незмінного знімка через `List.copyOf`;
- `find(Predicate<? super T>)` — пошук об'єктів за заданою умовою.

У `WeatherStationController` пряме зберігання
`List<WeatherReading>` замінено на
`Repository<WeatherReading>`.

Попередні обчислення та Stream API запити
продовжують працювати через `repository.all()`.

### Анотація @CsvColumn

Для опису CSV-стовпців створено власну анотацію:

`@CsvColumn`

Анотація має:

- `@Retention(RUNTIME)`;
- `@Target(FIELD)`;
- елемент `String value()`.

Поля `WeatherReadingRecord`, які експортуються,
позначено `@CsvColumn`.

Фактичний CSV-заголовок:

```text
дата,вологість,тиск,температура,вітер
```

Порядок стовпців є детермінованим і формується
за Java-іменами полів.

### Універсальний CSV-експортер

Створено універсальний `CsvExporter<T>`.

Експортер не залежить від `WeatherReadingRecord`
або іншого конкретного предметного класу.

За допомогою reflection він:

- отримує поля через `getDeclaredFields()`;
- залишає лише поля з `@CsvColumn`;
- перевіряє доступ до приватних полів;
- отримує назви стовпців з анотації;
- читає значення полів;
- формує CSV-заголовок і рядки.

Для CSV реалізовано коректне екранування:

- коми;
- подвійних лапок;
- перенесень рядка.

Запис виконується через `Path`, `Files`
та `StandardCharsets.UTF_8`.

Файл записується з `TRUNCATE_EXISTING`,
тому після повторного експорту в ньому
не залишаються старі рядки.

### Імпорт CSV і round-trip

Створено окремий `CsvParser`, який підтримує:

- розбір одного CSV-запису;
- розбір повного CSV-документа;
- quoted-поля;
- кому всередині лапок;
- `""` як одну подвійну лапку;
- multiline-поля;
- роздільники рядків `LF` і `CRLF`.

Некоректні CSV-лапки та неправильні символи
після закритих лапок завершуються
`DataStorageException`.

У `WeatherReadingRecord` реалізовано:

- `fromCsv(...)`;
- `fromFields(...)`.

Під час імпорту:

- дата відновлюється як `LocalDate`;
- числові значення відновлюються як `double`;
- повторно застосовується валідація моделі;
- хибні значення завершуються
  `DataStorageException` із початковою причиною.

CSV-файл читається через:

`Files.readString(..., StandardCharsets.UTF_8)`

Рядок заголовка не перетворюється
на предметний об'єкт.

Реалізовано повний round-trip:

`об'єкти → CSV → об'єкти`

Початковий і відновлений списки порівнюються
через `equals()`.

Для варіанта 18 після round-trip
зберігається ключ `date`,
порядок записів і всі значення полів.

### Обробка помилок

Для помилок збереження та відновлення даних
створено власний виняток:

`DataStorageException`

Він має:

- конструктор із повідомленням;
- конструктор із повідомленням і `cause`.

Розрізняються помилки:

- валідації моделі;
- формату CSV;
- значень CSV;
- файлової системи;
- reflection.

Початкова причина помилки не поглинається
і зберігається через `cause`.

### Зміни порівняно з Lab 4

У Lab 4 основний акцент був на Stream API
та обробці колекцій у пам'яті.

У Lab 5 додано окремий шар збереження даних:

- `Repository<T>` для роботи зі сховищем;
- `@CsvColumn` для опису CSV-метаданих;
- reflection для універсального експорту;
- `CsvExporter<T>` для запису CSV;
- `CsvParser` для повного розбору CSV;
- `WeatherReadingCsvStorage` для запису
  та читання погодних записів;
- `DataStorageException` для помилок збереження;
- round-trip перевірку відновлення об'єктів.

Попередній формат текстового звіту
та контрольні показники Lab 4 не змінено.

### Завдання із зірочкою

Реалізовано спільний generic-інтерфейс:

`Exporter<T>`

Через нього працюють два формати експорту:

- `CsvExporter<T>`;
- `JsonExporter<T>`.

JSON-експортер використовує ті самі
анотовані поля `@CsvColumn`,
що й CSV-експортер.

Для зменшення кількості повторних
reflection-операцій створено
`AnnotatedFieldResolver`.

Список анотованих полів кешується
окремо для кожного `Class<?>`.

Для оцінки ефекту кешування проведено
вимірювання на 5000 записах
і 10 ітераціях експорту.

Результат одного контрольного запуску:

```text
Without cache: 65.116 ms
With cache:    38.166 ms
```

Результат використовується як фактичне
вимірювання конкретного запуску і не
трактується як гарантований час
для кожного середовища.
